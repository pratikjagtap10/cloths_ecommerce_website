PART 2 - ARCHITECTURE  (4 min)
==========================================================================================

[DO] Show this diagram (or open BACKEND_DEVELOPER_GUIDE.md section 1)

                               Browser
                                  |
                       +----------v-----------+
                       |  NGINX API GATEWAY   |  http://localhost
                       +--+--------+-------+--+
                  /       |        |       |  /api/shop/*
          +-------v--+ +--v--------v--+  +-v--------------+
          | Next.js  | | CORE SERVICE |<-| SHOP SERVICE   |
          | frontend | | Django + DRF | R| FastAPI        |
          +----------+ | users,catalog| E| cart, checkout,|
                       | orders,admin | S| payments       |
                       +--+-------+---+ T+---+--------+---+
                          |       |  REDIS   |        |
                          |       +--events--+        |
                       core_db   core_worker       shop_db
                     (Postgres)  (listens)        (Postgres)

[SAY] Key points, one per box:
  - "The browser only talks to ONE address: the Nginx gateway. It routes
     /api/core to Django, /api/shop to FastAPI, everything else to Next.js."
  - "The CORE service in Django owns users, the product catalog and orders.
     It is the source of truth for prices and stock. It also gives us the admin panel."
  - "The SHOP service in FastAPI owns the cart, checkout and payments."
  - "Database per service: each service has its own PostgreSQL database.
     Neither service touches the other's database. They only talk through APIs or events."
  - "Redis is our message bus for asynchronous events."
  - "core_worker is the same Django code running as a background listener for events."

[SAY] Two ways the services talk, which is the heart of this project:
  1. SYNCHRONOUS REST: "FastAPI asks Django 'what's the price and stock of this item?'
     and WAITS for the answer."
  2. ASYNCHRONOUS EVENTS: "After payment, FastAPI announces 'payment succeeded'
     on Redis and DOESN'T wait. Django's worker picks it up and marks the order paid."

[SAY] Login: "Django issues a JWT token. FastAPI verifies the same token with a
       shared secret, so it never has to call Django to know who the user is."

PART 6 - RESILIENCE: WHAT IF A SERVICE GOES DOWN?  (3 min)
==========================================================================================

[DO]   Open a product page in the storefront first (so it's already loaded).
[DO]   Terminal B:
          docker compose stop core_service
[DO]   Click "Add to cart".
[TIP]  The button shows "Adding…" for about 10 SECONDS. That's expected: the shop
       service retries 3 times, and each DNS lookup of the stopped container
       takes a few seconds to fail. Fill the pause with the talking point below.
[SHOW] Friendly error: "Catalog service is unavailable. Please try again shortly."
[SAY]  "FastAPI retries the call with backoff, and every call has a timeout. When
        Django is still down, it returns a clean 503 with a readable message
        instead of crashing. Each service fails independently: browsing pages that
        were already loaded, the gateway and the shop service keep running."
[DO]   Terminal B:
          docker compose start core_service
          docker compose ps          (wait for healthy, ~15 s)
[DO]   Click "Add to cart" again: it works.

[SAY]  Honest limitation: "Redis Pub/Sub doesn't store messages. If the worker were down
        at the moment of payment, that order would stay PENDING. In production we would
        use Redis Streams, RabbitMQ or Kafka with an outbox pattern. This is documented
        as a known simplification."

PART 9 - TRADE-OFFS, LEARNINGS, NEXT STEPS  (2 min)
==========================================================================================

[SAY] Deliberate simplifications (it's a learning project):
  - Mock payment instead of Razorpay/Stripe webhooks
  - Emails are only logged
  - Pub/Sub can lose events (production: Streams/RabbitMQ + outbox pattern)
  - Tokens in localStorage (production: httpOnly cookies), DEBUG on, secrets in .env

[SAY] Interesting problems I hit:
  - Django rejects hostnames with underscores ("core_service"), so I added a
    "core-service" alias.
  - Nginx cached container IPs, so rebuilding one service gave 502s. Fixed with
    Docker DNS re-resolution.
  - Pages couldn't be pre-rendered at build time because the APIs don't exist during
    "docker build", so they render per request in real mode.

[SAY] Next steps: CI pipeline (GitHub Actions running pytest + Newman), real product
      images, frontend tests (Jest/RTL + Playwright), Redis caching for the catalog.

PART 10 - Q&A PREPARATION (likely questions and short answers)
==========================================================================================

Q: Why two backend frameworks instead of one?
A: To learn both and to show that microservices can use different tech. Django is
   strong for data-heavy CRUD plus a free admin panel. FastAPI is strong for fast async
   APIs with automatic docs. In a real company you'd choose per team/use case.

Q: Why does FastAPI call Django instead of reading the product table directly?
A: Database per service. If the shop read Django's tables, any schema change in
   Django could silently break the shop. The API is a stable contract.

Q: What if two users buy the last item at the same time?
A: Django's create_order uses SELECT ... FOR UPDATE inside a transaction. The second
   checkout waits, then sees stock is too low and gets a 409.

Q: Why not trust the price stored in the cart?
A: Prices can change, and a client could tamper with it. Django recalculates every
   line with its own current prices when creating the order.

Q: How does FastAPI know the user without calling Django?
A: JWT. Django signs the token with JWT_SECRET; FastAPI verifies the signature with
   the same secret and reads user_id from it. The verification is pure maths, with no network call.

Q: What happens when the access token expires?
A: The API returns 401. The frontend automatically calls /auth/refresh/ with the
   refresh token, saves the new access token and retries the request once.

Q: What if the same payment event arrives twice?
A: mark_order_paid is idempotent. It only acts when the order is still PENDING, so
   stock is never reduced twice. Confirming an already successful payment also does nothing.

Q: How are internal APIs secured?
A: Two layers: Nginx returns 404 for /internal/ from outside, and Django requires a
   shared X-Internal-Key header (compared in constant time).

Q: How would this run in production?
A: Same images. Push to a registry, run on Kubernetes/ECS, managed Postgres/Redis,
   HTTPS at the gateway/load balancer, secrets in a secret manager, DEBUG off.

Q: How long does it take to start?
A: First build ~10 min (downloads). After that, "docker compose up -d" takes ~30-60 s.

Q: How did you build the UI before the backend existed?
A: A mock API with the same interface as the real one, using JSON files with the same
   shapes as the planned APIs. When the backend was ready, one env variable switched
   it over and no page code changed. The same JSON files are now the backend's seed data.

BACKUP PLAN (if something breaks during the live demo)
==========================================================================================

- Page shows an error / 502       -> docker compose ps, wait for "(healthy)", refresh
- Login fails with 429            -> rate limit; wait 60 s (or use the other account)
- "Only N left in stock"          -> pick another size, or reset:
                                     docker compose exec core_service python manage.py seed_demo --force
- Order stays PENDING             -> docker compose restart core_worker, then place a new order
- Everything is broken            -> docker compose down && docker compose up -d
                                     (data is kept; add -v only to wipe everything)
- No internet / Docker issue      -> run the Postman collection results / Newman output
                                     you saved earlier, and walk through the diagrams instead

      npx newman run postman/Threads-Backend.postman_collection.json -e postman/Threads-Local.postman_environment.json > newman-result.txt
